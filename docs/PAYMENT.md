# 支付方案说明与面试题

项目保留两套可讲的支付方案：

- **模拟扫码付款（当前商城启用）**：用于稳定演示完整付款流程，不会发生真实扣款。
- **支付宝沙箱支付（历史已实现方案）**：用于说明第三方支付接入中“预创建订单、回调验签、金额校验、超时关单”的真实设计。当前商城不再依赖其稳定性。

本文不包含 AppID、私钥、公钥或公网地址。

## 1. 两套方案共用的业务主线

```text
顾客下单
  ├─ orders.status = PENDING_PAYMENT（待付款）
  ├─ 库存：available 减少，reserved 增加
  └─ payment_transaction.status = PENDING（首次打开付款码时创建）

付款确认成功
  ├─ payment_transaction.status = SUCCESS
  └─ orders.status: PENDING_PAYMENT → PAID

顾客取消 / 30 分钟超时
  ├─ orders.status: PENDING_PAYMENT → CANCELLED
  ├─ 库存：reserved 释放回 available
  └─ payment_transaction.status = CLOSED
```

`orders` 记录“买了什么、订单走到哪一步”；`payment_transaction` 记录“怎么付、付款码、是否成功、何时成功”。订单和支付流水分开后，后续接入支付宝、微信或模拟支付都不需要重做订单模型。

## 2. 当前启用：模拟扫码付款

1. 顾客在购物车或“我的订单”点击“模拟扫码付款”。
2. 后端创建 `MOCK` 支付流水，生成短时有效的随机付款码，并把项目内收银台 URL 生成二维码。
3. 手机扫码进入 `/mock-pay`，点击“确认模拟付款”。
4. 服务端校验付款码、有效期和订单仍为待付款后，条件更新订单为 `PAID`，同时写支付流水和状态历史。
5. 电脑端每 2 秒轮询本地订单状态，发现已付款后提示成功。

模拟付款码有效期为 30 分钟。订单取消或超时后，付款码关闭、库存回补，旧二维码不能继续确认付款。

## 3. 历史实现：支付宝沙箱支付方案

> 这一节保留为支付接入设计与面试回答。历史实现曾使用支付宝沙箱“当面付”二维码；实际演示已换为上面的模拟付款，避免沙箱 App 偶发不可用影响演示。

- 顾客下单后先进入 `PENDING_PAYMENT`，库存仅预占。
- 服务端调用 `alipay.trade.precreate` 预创建支付单，获得二维码内容后由 ZXing 生成图片；前端只展示二维码，不参与签名。
- 支付宝异步回调到服务端后，先做 RSA2 验签，再校验 AppID、商户订单号、订单状态和支付金额。
- 校验通过才将流水改为成功，并通过条件更新把订单从 `PENDING_PAYMENT` 改为 `PAID`。
- 超过 30 分钟未付款，定时任务取消订单、回补库存，并尝试调用支付宝关单。

沙箱联调时，二维码预创建曾成功返回 `10000`，说明网关、密钥和签名配置正常；但沙箱 App 偶发“服务繁忙”且不回调，因此将模拟扫码付款作为稳定的演示入口。

## 4. 支付专题面试题与参考回答

### 1）你的支付流程是怎样的？

顾客下单后订单先是待付款，库存只做预占。打开付款码时创建独立支付流水。当前项目用手机扫码进入模拟收银台确认付款；服务端校验付款码、有效期和订单状态后，才将订单更新为已付款。支付宝沙箱方案中，这一步由支付宝的服务端回调、验签和金额核对完成。两套方案共用同一套订单状态、流水和超时关闭逻辑。

### 2）为什么订单表之外还要有支付流水表？

订单描述“买了什么”，支付流水描述“怎么付、付没付成功”。付款编号、支付金额、渠道、回调原文、支付时间和关闭状态都属于支付领域。独立成表后，后续增加微信、支付宝或重试记录更自然，也方便对账和排查。

### 3）为什么不能由前端直接把订单改成已付款？

前端请求可以被伪造。如果前端传“订单号 + 已付款”就能绕过付款。模拟付款中，我用一次性付款码作为确认凭证，并由服务端重新校验订单；真实支付宝支付中，只信任验签后的支付宝服务端回调，不能信任浏览器页面。

### 4）支付宝回调验签具体是在防什么？

它证明通知确实来自支付宝，且内容没有被篡改。支付宝用私钥签名，商户用支付宝公钥验签。验签通过后还要核对 AppID、订单号和金额，避免将别的应用或别的订单的回调记到当前订单。

### 5）为什么验签通过后还要校验金额？

验签只证明报文可信，不代表一定对应当前订单。若商户订单号关联错误或业务参数传错，仍可能出现金额不一致。因此支付流水中的应付金额必须与回调金额一致；不一致就拒绝入账并记录日志。

### 6）重复回调或重复点击“确认模拟付款”怎么办？

订单更新使用条件更新，只有 `status = PENDING_PAYMENT` 的订单才能更新为 `PAID`。第一个请求成功后，后续请求更新行数为 0，只读取已处理结果，不会重复写状态历史或重复触发后续业务。

### 7）用户点了两次付款按钮，会创建两笔支付吗？

支付流水对“订单 + 支付渠道”有唯一约束。同一渠道重复打开时复用待支付流水；模拟付款会刷新付款码，使旧二维码失效。这样既避免重复付款，也避免截图长期有效。

### 8）为什么下单后不是直接扣减库存？

顾客还没付款，直接卖掉库存不准确；但完全不占库存会导致多人同时下单超卖。因此采用预占库存：下单时可售库存减少、预占库存增加；付款后继续履约；取消或超时未付款时释放预占库存。

### 9）订单超时关单怎么做？

定时任务每分钟扫描超过 30 分钟仍待付款的订单。先通过状态机取消订单并回补库存，再关闭本地待支付流水。支付宝方案还会尽力调用第三方关单；即使第三方网络失败，本地订单已是取消状态，后续回调也不能再把它改成已付款。

### 10）顾客手动取消订单时，怎样防止取消别人的订单？

取消接口从 JWT 取当前顾客 ID，跨商家读取订单后比较 `order.customerId`。只有订单属于当前顾客且仍为待付款，才允许取消。用户即使修改 URL 中的订单 ID，也不能取消其他人的订单。

### 11）为什么购物车跨商家要拆单、依次付款？

不同商家属于不同租户，库存、促销、收入、售后和商家确认都必须独立归属。购物车按商家拆成多笔订单，每笔订单各自生成支付流水和付款码，避免一个订单混入多个商家的复杂分账问题。

### 12）模拟收银台不登录，怎么保证安全？

扫码页面是公开页面，但它只能使用二维码里携带的高随机、短时有效付款码，不能按订单 ID 查询任意订单。服务端还会验证付款码状态、过期时间和订单是否仍为待付款。它适合模拟付款；真实资金支付仍必须使用第三方签名回调。

### 13）支付宝沙箱不稳定时，为什么不直接删掉支付设计？

不删。支付流水、状态机、金额校验、幂等更新和超时关单都是真实业务能力。沙箱不稳定只是第三方测试环境问题，所以用模拟扫码付款保证演示稳定，同时保留支付宝方案来说明真实接入时的完整安全要求。

### 14）以后接入真实支付宝或微信支付，需要改哪些地方？

订单状态机、支付流水、取消订单、超时关单和前端轮询都可复用。新增渠道实现负责创建第三方支付单和验签回调；回调成功后复用同一个“条件更新订单为已付款”的结算逻辑。真实渠道绝不能把手机页面的确认按钮当作付款成功依据。

## 5. 面试时可以主动说明的边界

- 当前商城的付款入口是模拟扫码付款，不会真实扣款。
- 支付宝沙箱方案是已实现过的第三方支付接入设计，包含预创建、RSA2 验签、金额校验与超时关单；因沙箱 App 偶发不可用，不作为当前演示依赖。
- 生产接入真实支付还需要商户签约、正式 AppID、正式密钥、稳定的 HTTPS 回调域名和支付安全审计。
- 支付成功后的发货、通知等后续动作可继续通过 Outbox + RabbitMQ 异步处理，避免支付确认线程承担过多业务。
