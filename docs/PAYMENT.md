# OrderFlow — 支付功能说明与面试题

> 本文记录当前支付宝沙箱支付实现、实际联调中遇到的问题，以及可直接用于面试的支付专题问答。文中不包含 AppID、私钥、公钥或公网回调地址。

## 1. 当前实现了什么

- 顾客按商家拆单后，订单初始状态为 `PENDING_PAYMENT`（待付款），库存已预占。
- 顾客可在购物车直接点击“支付宝付款”，或在“我的订单”中为任意待付款订单发起付款。
- 服务端调用支付宝沙箱 `alipay.trade.precreate`，拿到二维码内容后用 ZXing 生成图片；前端只负责展示，不参与签名。
- 每笔支付在 `payment_transaction` 中独立保存支付渠道、商户交易号、金额、状态、二维码内容、支付宝交易号、回调报文与支付时间。
- 支付宝异步回调到 `/api/payments/alipay/notify` 后，服务端验签、校验 AppID 和金额，再用条件更新把订单从 `PENDING_PAYMENT` 改为 `PAID`。
- 前端二维码弹窗每 2 秒轮询本地订单状态；只有服务端确认已付款，页面才显示成功。
- 超过 30 分钟未付款，定时任务自动取消订单、回补预占库存，并尽力调用支付宝关单。
- 顾客可手动取消自己的待付款订单；取消前会二次确认，取消后库存回补、待支付流水关闭，旧付款码不再可用于把订单改为已付款。

## 2. 状态与数据关系

```text
下单
  ├─ orders.status = PENDING_PAYMENT
  ├─ 库存：available 减少，reserved 增加
  └─ payment_transaction.status = PENDING（首次打开付款码时创建）

支付宝验签回调成功
  ├─ payment_transaction.status = SUCCESS
  └─ orders.status: PENDING_PAYMENT → PAID

顾客取消 / 30 分钟超时
  ├─ orders.status: PENDING_PAYMENT → CANCELLED
  ├─ 库存：reserved 释放回 available
  └─ payment_transaction.status = CLOSED（支付宝关单成功时）
```

`orders` 是业务订单，`payment_transaction` 是一次支付尝试的账务记录。两者分开后，订单金额、渠道流水、回调原文和支付结果都能分别追踪。

## 3. 本次支付宝沙箱排查记录

### 已确认正常的部分

1. 服务端实际使用的是新版沙箱网关：`https://openapi-sandbox.dl.alipaydev.com/gateway.do`。
2. 运行容器读取的是沙箱 AppID、沙箱应用私钥和沙箱支付宝公钥；未使用生产网关或生产密钥。
3. `alipay.trade.precreate` 返回 `10000`，说明二维码预创建请求和 RSA2 签名校验通过。
4. 浏览器跳转式支付已改为当面付二维码，顾客无需跳转支付宝网页收银台。

### 当前不稳定的部分

使用支付宝沙箱版 App 扫码时，App 偶发“人气太旺啦，稍候再试试”提示。此时项目服务端没有收到支付回调，说明失败发生在沙箱 App 发起付款请求阶段，而不是订单创建、二维码生成、网关选择或本地密钥配对阶段。

### 结论与后续方案

当前代码保留支付宝沙箱通道，适合展示“支付流水 + 回调验签 + 状态机 + 超时关单”的完整设计；但演示时不应依赖沙箱 App 的可用性。下一步可增加独立的“模拟扫码付款”通道：二维码跳转至项目自身的模拟收银台，以一次性、短时有效的随机支付令牌确认付款，不扣真实资金，但仍复用支付流水、幂等控制、订单状态与关单逻辑。

## 4. 面试题与参考回答

### 1）你的支付流程是怎样的？

顾客下单后，订单先是“待付款”，库存只做预占，不算真正成交。顾客打开付款二维码时，我创建一条支付流水。支付宝支付成功后不会相信前端页面，而是等支付宝服务端回调；回调验签、核对金额和 AppID 都通过后，才把支付流水改为成功，并把订单改成“已付款，待商家确认”。

### 2）为什么订单表之外还要有支付流水表？

订单描述“买了什么”，支付流水描述“怎么付、付没付成功”。一个订单会有渠道交易号、支付金额、回调报文、支付时间、关闭状态等支付专属信息，直接塞进订单表会让订单领域和支付领域混在一起。独立出来以后，后续增加微信支付、模拟支付或重试记录也更自然。

### 3）为什么不能由前端扫码成功后直接把订单改成已付款？

前端数据不可信，任何人都能在浏览器里伪造请求。如果前端能直接改状态，就能绕过真实付款。正确做法是只信任支付渠道的服务端回调；回调先验签，再核对金额、AppID、商户交易号，全部一致才更新订单。

### 4）支付宝回调验签具体是在防什么？

它是在证明“这条通知确实来自支付宝，而且内容没有被中途篡改”。支付宝用自己的私钥签名，我用支付宝公钥验签；验签失败就不处理。即使验签通过，我还会继续比对 AppID、订单号和金额，避免把别的应用或别的订单的回调误记到当前订单。

### 5）为什么还要校验支付金额？

验签只证明报文来源可信，不代表它一定对应当前订单。比如错误关联了交易号，或者业务参数传错了，都可能造成金额不一致。所以支付流水里的应付金额和回调里的 `total_amount` 必须相等，不相等就拒绝入账并记录错误日志。

### 6）重复回调怎么办？

支付平台可能重复通知。我对订单使用条件更新：只有 `status = PENDING_PAYMENT` 的订单才能更新为 `PAID`。第一条回调更新成功后，后面的回调更新行数为 0，只按“已处理”返回成功，不会重复写支付成功记录，也不会重复触发后续业务。

### 7）用户点了两次“支付宝付款”，会创建两笔扣款吗？

不会。支付流水对“订单 + 支付渠道”有唯一约束。第一次创建出待支付流水和二维码后，第二次会复用同一条待支付流水和同一个二维码，而不是再创建新的商户交易号。

### 8）为什么下单后不是直接扣减库存？

顾客还没有付款，直接把库存卖掉会不准确；但完全不占库存又可能被多个顾客同时下单导致超卖。所以我采用“预占库存”：下单时可售库存减少、预占库存增加；付款后继续履约；取消或超时未付款时，再把预占库存释放回来。

### 9）订单超时关单怎么做？

定时任务每分钟扫描超过 30 分钟仍为待付款的订单。它先走订单状态机取消订单并回补库存，然后尽力调用支付宝关单，最后把本地支付流水标记为关闭。即使第三方关单网络暂时失败，订单本地也已经是取消状态，后续回调不会再把它改成已付款。

### 10）顾客手动取消订单时，怎样防止取消别人的订单？

取消接口从 JWT 中取得当前顾客 ID，跨租户读取订单后先比较 `order.customerId` 是否等于当前顾客 ID。只有订单属于当前顾客并且仍是待付款，才允许取消。这样顾客不能通过修改 URL 中的订单 ID 取消其他人的订单。

### 11）为什么购物车跨商家要拆单、依次付款？

不同商家属于不同租户，收入、促销、库存和售后都要独立归属。一次订单混进多个商家会让分账、退款和商家确认变得复杂。因此购物车按商家拆订单；付款时为每笔订单生成独立支付流水和二维码，前端按顺序引导顾客完成付款。

### 12）支付宝沙箱不稳定时，你会怎么保证项目可演示？

我会把支付渠道抽成接口，支付宝沙箱只是其中一个实现，再提供本地模拟扫码支付。模拟支付仍创建支付流水、生成二维码、校验一次性支付令牌、控制幂等并驱动同一套订单状态机。这样第三方沙箱不可用时，核心支付业务链路仍然可以稳定演示；上线环境只启用真实渠道即可。

## 5. 面试时可以主动说明的边界

- 当前接入的是支付宝**沙箱**，不会发生真实扣款；生产环境还需要商户签约、正式 AppID、正式密钥和稳定的 HTTPS 回调域名。
- 支付宝沙箱二维码预创建已验证成功，但沙箱 App 付款端偶发服务繁忙，因此正在补充本地模拟扫码通道作为演示兜底。
- 支付成功后的发货、通知等后续动作可继续通过现有 Outbox + RabbitMQ 异步处理，避免支付回调线程承担过多业务。
