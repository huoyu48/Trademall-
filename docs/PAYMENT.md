# 模拟扫码支付

> 当前商城不再调用支付宝沙箱或任何真实支付渠道。付款功能用于完整演示电商支付链路，**不会扣款**。

## 顾客看到的流程

1. 顾客在购物车点击“模拟扫码付款”，系统按商家拆单并创建待付款订单。
2. 电脑端展示付款二维码；二维码指向项目自己的 `/mock-pay?token=...` 模拟收银台。
3. 顾客用手机扫码，在手机页面点击“确认模拟付款”。
4. 服务端确认付款码和订单仍有效后，把订单由 `PENDING_PAYMENT` 条件更新为 `PAID`，并写入状态历史和支付流水。
5. 电脑端每 2 秒轮询订单状态；发现已付款后自动提示成功。顾客也可以在“我的订单”继续付款或取消订单。

手机扫码需要能访问商城地址。因此本地用手机演示时，在 `.env.local` 配置：

```properties
ORDERFLOW_MOCK_PAYMENT_PUBLIC_BASE_URL=https://你的公网地址
```

例如 Cloudflare Tunnel 指向本机 `8088` 后，把它分配的 HTTPS 地址填入即可。若只在电脑浏览器测试，默认的 `http://localhost:8088` 即可。

## 服务端保护点

- `payment_transaction` 独立保存付款编号、金额、渠道（`MOCK`）、状态、二维码内容、付款码、过期时间与确认记录；订单与付款流水分开，后续可替换为真实渠道。
- 付款码是 64 位随机 token，只能对应一笔待付款订单；每次重新展示二维码都会更新 token，旧二维码立即失效。
- 手机端不能传“金额”或“订单状态”。服务端从流水与订单读取金额，并以 `UPDATE ... WHERE status = 'PENDING_PAYMENT'` 条件更新订单，重复确认只会成功一次。
- 付款码有效 30 分钟，与订单超时取消保持一致。订单被顾客取消或超时取消后，未完成的付款流水都会变为 `CLOSED`，二维码不再可用，库存会回补。
- 这是模拟支付，不应把公开 token 设计直接复用到真实支付。接入真实支付时，仍应以第三方签名回调为准，而不是信任网页按钮。

## 支付相关面试题

### 1. 为什么订单和支付流水要分表？

订单记录“买了什么、多少钱、现在处于什么履约阶段”；支付流水记录“用什么方式付、付款码、是否成功、何时成功”。一次订单可能重试付款、换支付渠道，分表后不会把支付细节塞进订单表，也便于后续对账和排查。

### 2. 你的模拟扫码付款是怎样完成的？

电脑端下单后，后端创建一条 `MOCK` 支付流水，生成随机付款码和对应的项目内收银台 URL，再生成二维码。手机扫描二维码后只能看到该笔付款，点击确认由后端校验付款码、订单状态和有效期；校验通过才把订单改成已付款。电脑端只是轮询结果，不直接改订单状态。

### 3. 为什么不能让前端直接把订单改为已付款？

前端运行在用户浏览器里，任何人都可以改请求内容。若提供“订单号 + 已付款”的接口，用户可以绕过付款。即使是模拟支付，也应把确认动作放在带随机付款码的手机收银台接口，并由服务端再次校验订单状态；真实支付则必须由支付平台的验签回调确认。

### 4. 如何避免同一个二维码被重复确认？

订单更新使用带旧状态的条件更新：只有当前仍是 `PENDING_PAYMENT` 的订单才能更新成 `PAID`。第一个请求更新成功后，后续请求影响行数为 0，只会读到已付款结果，不会重复写状态历史或重复扣库存。

### 5. 顾客取消订单或超时未付款怎么办？

取消时先把订单状态流转到 `CANCELLED` 并回补预占库存，再将该订单所有仍为 `PENDING` 的支付流水关闭。定时任务每分钟扫描超过 30 分钟的待付款订单，执行相同的关闭和回补逻辑，因此旧二维码即使被扫到也不能再付款。

### 6. 为什么模拟支付还要设计付款码过期？

过期能防止截图或旧链接长期有效，也让演示流程更接近真实收银台。每次电脑端重新打开付款二维码都会刷新付款码，旧码失效；30 分钟后未付款订单会被自动关闭。

### 7. 以后如何替换成真实支付宝或微信支付？

订单状态机、支付流水、取消订单、超时关单和前端轮询可以继续保留。只需新增支付渠道实现：创建真实支付单后把第三方交易号写入流水；收到并验签第三方回调后，复用同一个“条件更新订单为已付款”的结算方法。真实渠道不能把手机页面的确认按钮当作付款成功依据。
